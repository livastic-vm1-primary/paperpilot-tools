ENGLISH CHECKLIST

6 checkpoints before you call a project delivered

  1. Write down the scope. Document the buyer's desired outcome, excluded work, deliverable format, deadlines, revision count and acceptance criteria. This prevents invisible scope creep.
  2. Send a clear quote. Itemize work, units, fees, applicable discounts, payment milestones, and the quote expiry date. A quote is a proposal; it is not itself proof that payment was received.
  3. Protect your workflow. Before handing over a repository, review GitHub Actions token permissions, which events run privileged jobs, third-party action versions, untrusted expression interpolation, and secret exposure. A static preflight can highlight suspicious patterns but cannot prove safety.
  4. Verify delivery. Run documented tests. Provide access, installation instructions, build artifacts, important limitations, a change summary and a handoff checklist. Avoid publishing clients' credentials in issues or screenshots.
  5. Create an invoice. State seller and buyer details, what was delivered, a unique reference, invoice date, payment terms and currency. Record the applied discount, tax if appropriate, payments already received and amount due.
  6. Close the loop. Keep a private copy of the final invoice, signed approvals and payment confirmation. Ask for permission before publishing testimonials or work samples; never manufacture reviews.

Quote vs. invoice

Quote / estimateInvoice
Used before agreement or before deliveryUsed to request payment for agreed work
Shows expected work, pricing, and validityShows completed/contracted items and payment terms
Customer can accept or request changesCustomer can pay or reconcile what is due

Local compliance matters. This is a workflow guide, not accounting or legal advice. PaperPilot generates printable invoice/quote documents, not government-certified e-tax invoices. Currency selection is for formatting only; no exchange rates are fetched.

한국어 체크리스트

고객에게 납품하기 전 6가지 확인 사항

  1. 업무 범위를 문서화하기. 목표, 제외 항목, 납품 형식, 일정, 수정 횟수, 검수 기준을 정리합니다. 추후 추가 요청이 있을 때 합의 기준이 됩니다.
  2. 견적서 항목 구분하기. 서비스별 수량과 단가, 할인, 결제 단계, 견적 유효기간을 명확히 표시합니다. 견적서는 결제가 완료됐다는 증빙은 아닙니다.
  3. 자동화 설정 점검하기. GitHub Actions의 토큰 권한, 외부 액션 버전 고정, 외부 PR 실행 조건, 셸 삽입 가능성, 시크릿 노출 위험을 검토합니다. 정적 점검 도구는 위험 신호를 표시할 뿐 보안을 보증하지 않습니다.
  4. 납품물 검사하기. 테스트 결과, 설치·운영 방법, 변경 내용, 알려진 한계, 인계 목록을 전달합니다. 공개 이슈나 스크린샷에 고객 비밀번호를 넣지 않습니다.
  5. 청구서 정리하기. 공급자·고객 정보, 문서 번호, 청구일, 통화, 결제 기한, 서비스 내역, 세금·할인·선결제 금액을 확인합니다.
  6. 후속 처리 기록하기. 계약과 납품 동의 기록, 청구서, 실제 입금 확인을 보관합니다. 사례나 후기 공개 전에는 고객 동의를 받습니다.
